What is already agreed, and is not reopened here

These were settled in the proposal and in review. The plan below assumes every one of them. If any changes, the phase that depends on it changes with it — so they are listed first, in one place, rather than scattered through the steps.

Identity

  • No new role. A fundraiser is a supporter. Role decides which portal a person lands in, and that does not change.
  • No new EnumModule value. EnumModule is the product catalogue and a billing dimension — a new value is a new SKU. Peer-to-peer is a feature inside the Donation module.
  • An isFundraiser claim in the JWT decides whether the fundraiser menu item draws. It is derived at token issue from live participation rows, never stored, never granted, never revoked by hand.
  • The claim decides pixels only. Every endpoint authorises server-side against participation rows for that user and that campaign, deny by default.

Shape

  • Role is capability, row is participation. Being a fundraiser is a row per campaign, not a property of the person.
  • The participation table does not exist yet. Verified against ideali.api: every FundRais* symbol in the backend today is DonationCampaign.FundRaisingGoal, a decimal? money target. The table is new work, and it is inside this project’s scope.
  • No impact on other modules. New tables and new routes, plus exactly two nullable columns on existing donation tables — the peer-to-peer flag on DonationCampaign and the attribution key on DonationCampaignInvoice. Both go in nullable, with no backfill and no row rewrite. No change to donor or member navigation.
  • Charities invite, they never add. Nobody becomes a fundraiser without accepting.
Two limitations we ship with, deliberately, and say out loud.
  1. The fundraiser menu appears at next sign-in, not instantly. The claim is written at login, and allowedModules in src/routes/memberRoutes.tsx is a top-level constant evaluated once when the bundle loads — a React re-render will not re-evaluate it. Logging out and back in resets both layers because it is a full page load. Accepted as the interim behaviour; the automatic fix is its own change, not smuggled into this one.
  2. Leaving has no such reset. When somebody’s last campaign ends, the menu item survives until their next sign-in. That is why phase 8 puts a designed empty state behind it rather than a dead screen. This one is not deferred — it is a build item.
Repo reality this plan is written against. This repository has no ESLint config, and until the approved Vitest commit lands it has no test runner either — npm run build is the only automated gate that exists today. So every phase gate below is a manual script run by a person, plus a clean build, and the automated coverage that Vitest adds sits on top of that rather than replacing it. How those gates work, who runs them and what makes one pass is set out in How each phase is tested.

The five decisions that were blocking this plan, and how each one was settled

These were open questions when the proposal went out. All five were answered in review on 20 August 2026 and are locked — decision made, spec written, buildable. Every phase below assumes them. They are recorded here in full so that nobody has to reconstruct them from a conversation.

Blocker 1 Where peer-to-peer lives

Peer-to-peer is a feature inside the Donation module, not a product of its own. It is switched on per campaign by an IsPeerToPeerEnabled flag on DonationCampaign. No new EnumModule value is created, because EnumModule is the billing catalogue — a new value is a new SKU, with a price, a subscription line and a migration behind it.

Authorisation is on campaign ownership, checked server-side on every endpoint, deny by default. Never on a role name, never on a module grant.

Blocker 2 What “raised” means

One definition, computed by one backend query that every surface calls — fundraiser page, team page, organiser list, leaderboard. Two implementations of this number is how a leaderboard and a report end up disagreeing in front of a donor.

QuestionLocked answer
Tips to IdealiExcluded. A tip is platform revenue, not money raised for the cause.
Processing feesCounted gross. The donor gave that amount, so that is what the page shows.
Pending paymentsExcluded. Settled transactions only.
Refunds and chargebacksSubtract. The total can go down.
Recurring donationsCounted per settled installment, not as a promised annual total.

Blocker 3 How a donation is attributed to a fundraiser

One nullable column, CampaignFundraiserId int NULL, on DonationCampaignInvoice. It is write-once — set when the donation is created through a fundraiser page, never edited afterwards, because editing it moves money between two people’s totals after the fact. It is never promoted to NOT NULL: every donation that already exists, and every direct donation from now on, legitimately has no fundraiser.

The migration adds a nullable column and a filtered index. No backfill, no row rewrite, no table rebuild on a shipped table.

ALTER TABLE dbo.DonationCampaignInvoice
ADD CampaignFundraiserId int NULL;
GO

ALTER TABLE dbo.DonationCampaignInvoice
ADD CONSTRAINT FK_DonationCampaignInvoice_CampaignFundraiser
    FOREIGN KEY (CampaignFundraiserId) REFERENCES dbo.CampaignFundraiser(Id);
GO

CREATE INDEX IX_DonationCampaignInvoice_CampaignFundraiserId
    ON dbo.DonationCampaignInvoice (CampaignFundraiserId)
    WHERE CampaignFundraiserId IS NOT NULL;

The index is filtered because the overwhelming majority of rows stay NULL forever, and an unfiltered index on that column is mostly dead weight.

Blocker 4 One person fundraising for more than one charity

Business confirmed on 20 August 2026 that a fundraiser may belong to several charities run by different organisations. That is a genuine cross-OrganizerId relationship, not a sub-profile inside one charity.

Chosen shape (Option B): a UserContact(UserId, ContactId, OrganizerId) membership table. One login, one person, many charity memberships.

Rejected (Option A): a separate account per charity, keyed on a per-charity unique email. It makes sign-in ambiguous when one address matches several accounts, and it requires dropping a unique index that is live in production today.

Membership is consent-first. The charity sends an invitation, the fundraiser accepts, and only then is the row written. A charity may never add a person to itself unilaterally.

The sequencing is part of the lock, not a detail.
  1. Handle the duplicate-account collision at Donation.DonateService.cs:218-224 now, so the current failure stops being a raw exception.
  2. Ship the collision screen now, so a person who hits it is told what happened and what to do next.
  3. UserContact itself is a separate project that starts after peer-to-peer has shipped — it is not phase 7 of this plan, and it appears nowhere in the eight phases below. It rewrites how identity works across the whole platform, and that does not belong inside a feature branch.
The login path is not touched by this, and that was verified in the code rather than assumed.

Signing in runs exactly one chain: AccountService.AuthenticateAsync → GetUserForTokenAsync → TokenService. That chain reads User.UserName, the password hash, and u.Contact.Organizer — which is reached through User.ContactId. So the login path does depend on User.ContactId, and any plan that claimed otherwise was wrong.

That dependency is what makes the design safe rather than risky, because of one rule: User.ContactId keeps its current meaning and keeps being written, permanently. It stays the person’s home charity, it stays the source of the OrganizerId claim in the token, and it is never dropped. UserContact only ever adds extra memberships alongside it; it never becomes the thing sign-in reads.

  • Five files are locked for the duration. Identity/…/AccountService.cs, Identity/…/TokenService.cs, Middleware/ClaimStoreMiddleware.cs, Identity/Controllers/IdentityBaseController.cs and Identity/Controllers/TwoFaController.cs. If a UserContact commit produces a diff in any of them, that commit is wrong — regardless of whether the build is green.
  • The 199 existing reads of the OrganizerId claim do not change. Every module scopes its data by that claim today. Re-pointing it at a membership table would put a cross-charity data leak behind 199 separate call sites, so it is not re-pointed at all.
  • Only new endpoints consult UserContact. A cross-charity fundraiser page authorises against an accepted membership row for the organiser named in the route, checked server-side. Existing endpoints keep behaving exactly as they do today.
  • No migration rewrites a shipped row. The table is additive, the backfill is insert-only in batches, and no UPDATE and no lock ever lands on User.

The full design lives in docs/multi-organiser-account-plan.html.

Blocker 5 The public URL of a fundraiser page

The shape is /campaigns/{campaignSlug}/{fundraiserSlug}. A fundraiser slug is unique within its campaign, not globally — two campaigns may each have a sarah-khan, and global uniqueness would hand the first Sarah a name the second one can never use.

CREATE UNIQUE INDEX UX_CampaignFundraiser_Campaign_Slug
    ON dbo.CampaignFundraiser (DonationCampaignId, Slug)
    WHERE IsDeleted = 0;
  • The index is filtered on IsDeleted = 0 because CampaignFundraiser is soft-deleted. Without the filter, a deleted page holds its slug hostage forever.
  • No backfill UPDATE on existing campaigns. A campaign slug is generated when peer-to-peer is switched on, not retroactively across a shipped table.
  • Non-ASCII display names collapse to nothing. When fewer than three characters survive slugging, the slug falls back to fundraiser-{shortId}.
  • Slugs are forced lowercase on write, so the uniqueness check cannot be defeated by casing.
  • A reserved-word blocklist rejects admin, api, auth, login, donate, new, edit and settings, so a fundraiser page can never shadow a platform route.

The three email work items that came out of blocker 7.
  1. There is no suppression list. No send path checks for a bounce, a spam complaint or an unsubscribe before sending, and delivery feedback is wired up for membership alerts only. A peer-to-peer invitation run will send to dead addresses and damage sending reputation. Built in phase 7.

The DNS authentication verified on 20 August 2026 covers the default sender only.

How each phase is tested, and what “done” means

Every phase below ends with a test gate, and the gate is the definition of done for that phase. A phase whose gate has not been run is not finished, however green the build is. The gates were agreed for one reason: nobody should have to take our word that a phase works.

What a gate contains

  • What a person can open and try. One sentence naming the thing that is demonstrable at the end of the phase. If it cannot be demonstrated in a browser, the phase was scoped wrong.
  • Set up before you start. The accounts, campaigns and data the script needs. Gathered before the gate day, not during it.
  • The numbered script. Run in order, by a person, on a real environment.
  • Passes only when. The bar. Every gate names a condition that a clean build alone does not satisfy.

Who runs it

  • From phase 2 onward, at least one step is run by somebody who did not build the feature. A developer walking their own screen finds nothing.
  • The organiser-facing gates are signed off by a person who actually runs campaigns, not by the developer who wrote the screen.
  • Every gate run is recorded: date, who ran it, what failed, what was fixed before it was called passed.
  • A failed step is a phase that has not ended. It is not carried into the next phase as a known issue unless leadership is told and agrees in writing.
These gates stay manual even once the runner lands. Vitest was approved on 20 August 2026 and goes in as its own commit before the frontend phases, so frontend work from that point ships with unit and component coverage. What Vitest does not cover is a person taking real money through a real fundraiser page on a real merchant — and that is exactly what these gates check. Playwright was not approved, so there is no automated browser test to fall back on. Backend work goes in with its own tests, in the existing tests/Ideas.API.Tests project. Until the Vitest commit lands, npm run build is still the only automated gate the frontend has.
Two gates depend on something we do not have yet. Phase 3 and everything after it take real money on a test merchant, and that needs the blocker 9 test environment: a real test campaign, a Stripe test merchant connected to it, and the ability to produce a refund, a tip, a pending payment and a recurring donation. That environment is needed before phase 3 starts, not when it ends. If it is not there, phase 3 is blocked rather than shipped untested.

Test at the end of phase 1

What a person can open and try. An organiser signs in, opens a real donation campaign, finds the peer-to-peer tab and switches the feature on. Nothing is public yet — this phase proves the data model and the switch, not the product.

Set up before you start. One donation campaign owned by the test organiser. A second organiser account owning a different campaign, for the refusal tests. One supporter account. Direct database access, to insert and soft-delete a CampaignFundraiser row by hand.

  1. Switch peer-to-peer on and save. Reload — the setting persisted. Set each of the five settings, save, reload — all five persisted.
  2. Switch it off. The confirmation names the consequence in plain words. Reload — off.
  3. Sign in as the organiser who does not own that campaign and call the settings endpoint directly. Refused, and the refusal says nothing about whether the campaign exists.
  4. Insert one CampaignFundraiser row by hand, sign that user in, decode the token: isFundraiser is present. Soft-delete the row, sign in again: it is gone.
  5. Refresh the token without signing in again. isFundraiser survives the refresh — it is emitted on the refresh path, not only at first sign-in.
  6. Migration safety, checked before it is run anywhere. Read the generated migration: it adds nullable columns and creates indexes, and contains no backfill UPDATE and no table rebuild. Record DonationCampaign row count and the newest audit timestamp before and after — both unchanged.
  7. Slug rules from blocker 5. A display name that slugs to fewer than three characters yields fundraiser-{shortId}. Admin is rejected by the blocklist. Two people named Sarah Khan on one campaign get distinct slugs, and the same name on a different campaign is accepted unchanged.
  8. Soft-delete a fundraiser row, then create a new one with the same slug on the same campaign. Accepted — the filtered index released the name.
  9. npm run build clean, no new warnings.

Passes only when. Every step above passed on a real campaign, the migration was read line by line before it ran, and the person who ran the script is named with the date. A green build alone is not this gate.

What is now automated, and what is not. Steps 1, 2, 3, 7 and 8 run on every npm run test:e2e against the live API and the real database — settings persistence, the switch-off confirmation, cross-tenant refusal that reveals nothing, slug rules, and the filtered index releasing a name after a soft delete. Step 9 is npm run build. Steps 4 and 5 — the isFundraiser claim surviving sign-in and a token refresh — are covered by FundraiserClaimTests and RefreshTokenFundraiserClaimTests. The latter drives AccountService.RefreshToken itself against an in-memory database, so the claim is asserted on the token a long session actually receives, and a replayed or expired refresh token is proven to mint nothing. Neither has browser-level proof yet, because nothing in the product creates a fundraiser row. Step 6, migration safety, was a one-off read of a migration that has already run; it cannot be re-run and is not automatable.

What is automated, and what is not. Steps 2 to 6, 8 and 9 run on every build: peerToPeerJoin.api.spec.ts drives the real endpoint and reads each row back out of the database with SQL, and peerToPeerJoin.ui.spec.ts walks the browser journey at 1280, 768 and 375 px. campaignPeerToPeerSlug.database.spec.ts proves the new campaign-address index on the live schema. Three things are not covered and are named here rather than assumed. Step 1 no longer sends anybody to another screen. A visitor asking to fundraise without a session is offered both ways in on the campaign itself: a modal with a Sign in tab and a Create account tab. Signing in there returns them straight to the fundraising page; the session is established by the same shared code the sign-in screen uses, two-factor verification included, so this surface cannot become a way around a check the account owner asked for. Creating an account does not sign anybody in. It issues a single-use token, emails a link, and the join endpoint refuses any account holding an unconfirmed address until that link has been followed. What is stored is a SHA-256 digest and never the token, unknown, expired, spent and issued-for-another-campaign all answer with one sentence, and asking for a new link retires every outstanding one. The gate is deliberately narrow: EmailConfirmed has existed on User since the first migration and nothing ever set it, so only accounts that were actually sent a link are held to one — existing organisers are not locked out of their own campaigns. Covered by SupporterSignUpServiceTests, EmailVerificationServiceTests, EmailVerificationControllerTests and the join-gate tests in FundraiserJoinServiceTests on the backend; FundraiseAccessModal.test.tsx, VerifyEmailPage.test.tsx, completeLogin.test.ts and emailVerificationService.test.ts on the frontend; and peerToPeerEmailVerification.api.spec.ts, peerToPeerAccess.ui.spec.ts and emailVerification.database.spec.ts end to end. One limit stands: the account is scoped to the charity running the campaign it was created from, so the same address cannot sign up again at a second charity (it signs in instead). Joining a second charity's campaign still works. Step 7, the duplicate-email collision screen, was not built: today a collision surfaces as an error toast carrying the server’s sentence, and replacing it with a designed screen changes the shared production sign-up form, which is its own approved change. And the address a supporter is shown does not resolve yet — the public page it points at is phase 3.

Test at the end of phase 3

What a person can open and try. A donor who has never signed in opens a named fundraiser’s page and gives real money through it. At the end of this phase the feature earns.

Set up before you start. This is the phase that needs the blocker 9 test environment, and it cannot start without it: a real test campaign, a Stripe test merchant connected to that campaign, and the ability to produce a refund, a tip, a pending payment and a recurring donation. Plus two fundraiser pages on the same campaign, so attribution can be told apart.

  1. Open a fundraiser page signed out. It renders. Nothing private is in the page source or in the network response — no email address, no user identifier, no donor contact details.
  2. Donate with a test card. The gift appears on that fundraiser’s page, on the campaign total, and in the organiser’s existing reports. The campaign total went up once, not twice.
  3. Donate directly to the campaign, not through any fundraiser page. The invoice row carries CampaignFundraiserId = NULL and no fundraiser total moved.
  4. Blocker 2, checked one line at a time. Add a tip to a donation: the raised total ignores the tip. Leave a payment pending: it is not counted until it settles. Refund a settled donation: both totals drop. Set up a recurring donation: only settled installments count, not the promised annual figure.
  5. Confirm the number is one query, not two. The fundraiser page, the campaign page and the organiser report show the same figure for the same fundraiser at the same moment.
  6. After the refund, read the invoice row: CampaignFundraiserId is unchanged. Attribution is write-once — the money moved, the credit did not.
  7. Donate anonymously. The page shows the gift, not the person.
  8. Paste a script tag into the fundraiser story. It renders as text on the public page.
  9. Open an unknown slug, a hidden page and a closed campaign. Three designed screens, no stack trace, no backend identifier, no framework detail.
  10. Return from the payment provider in a new tab. Attribution survived the round trip.
  11. Submit the donation twice quickly. No money counted twice.
  12. The whole donation flow on a phone at 375px, then at 768 and 1280.

Passes only when. Real money moved on a test merchant, the raised figure matched the blocker 2 definition on every one of the five cases, and the organiser reconciled the number against the existing donation dashboard and signed it off. Organiser approval notice

Every screen, every width

Raised in phase 3, and worth a decision.
  • Recurring donations needed a second column. Blocker 3 locked one nullable column on DonationCampaignInvoice. That alone credits only the first installment of a recurring gift, because every later installment is invoiced by a background job that has no idea which page the schedule started on. DonationRecurring therefore carries the same nullable column, and the job copies it forward. Same shape, same filtered index, no backfill — but it is one column more than the blocker described.
  • Donor messages are not published. The leadership design shows a short quote beside each recent gift. Donation notes exist today as an organiser-facing field; nobody has agreed with donors that what they write there becomes public. Publishing them would need a consent checkbox on the donation form. The supporters list therefore shows a name, an amount and a date, and no message.
  • Photos are phase 4. The design shows the fundraiser’s own photo. Uploading one belongs to the edit screen, so the page shows initials until then.
  • Social preview tags are written by script. A crawler that does not execute JavaScript sees the application defaults. Fixing that properly means server-side rendering, which this stack does not have and which is not worth adding for one screen.
